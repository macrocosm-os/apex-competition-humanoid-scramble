# Rendering Box Scramble

What the dashboard's course preview and submission viewer need in order to render this
competition, and where it differs from Humanoid Parkour, which it is forked from.

Short version: **the record envelope is identical to parkour's, and four things inside it are
not.** None of the four is hard, but none of them is automatic either.

## What is already the same

Measured by diffing a real parkour record against a real Box Scramble one:

| | parkour | box_scramble |
|---|---|---|
| top-level keys | `conditions format frames instance match_id mujoco_version num_instances outcome timing` | **identical** |
| `outcome` keys | `distance_m progress score sim_time_s steps terminal_reason` | **identical** |
| `timing` keys | `control_dt frame_skip phys_dt stride` | **identical** |
| array packing | `{dtype, shape, b64}`, float32/int32 | **identical** |
| control rate | 50 Hz, stride 2 by default | **identical** |

So a reader that walks the envelope, unpacks arrays and drives a model from `frames.qpos` needs no
structural change.

## The four differences

### 1. `format` is `box_scramble_history/2`

Parkour writes `humanoid_parkour_history/1`. A reader that whitelists the exact parkour string will
reject every file this competition produces. Match on the family, or add this one.

The trailing number is the format's own version and will move independently of the competition
version: `/1` wrote a different frame layout (see §2) and files in that shape may still exist.

### 2. The robot is 22-DoF, so `frames.nq` is 29, not 19

This robot has full arm control — 12 leg joints plus 10 arm joints (shoulder pitch/roll/yaw, elbow,
wrist roll, per side) — because pushing, lifting and climbing are the task. Parkour's is legs-only.

- `frames.nq` = **29** (7 free-joint + 22 actuated) where parkour's is 19
- the model is `env/assets/g1_22dof.xml`, not `g1_12dof.xml`, and it vendors arm and hand meshes
  parkour's asset set does not contain
- `frames.action` is 22 wide, not 12

A viewer pointed at the 12-DoF skeleton will mis-map every joint. This is the difference most
likely to produce a silently wrong render rather than an error.

### 3. `conditions` carries the box field, not friction

| parkour | box_scramble |
|---|---|
| `friction_level`, `frictions` (per-geom array) | `box_field` |
| `wind_speed_ms`, `wind_dir_deg` | `wind_speed_ms`, `wind_dir_deg` |

`box_field` is `{fields, zones, values}`: one row per box, columns
`cx cy cz hx hy hz density yaw`, plus a parallel list of zone labels
(`scramble` / `push` / `climb`). Half-extents, so double them for a renderer that wants full sizes.

Neither the round seed nor the per-instance seed appears in a record, by design. The conditions are
what the run faced, not the inputs that produced them.

### 4. There are 196 boxes, and they move

This is the real work. Parkour's scene is static geometry; here the obstacle *is* a field of loose
free bodies, and a replay that draws only the robot shows nothing of what happened.

`frames.boxes` carries:

- `rest` — `(n_boxes, 7)` free-joint pose (position + quaternion) for **every** box at frame 0
- `indices` — which boxes moved during the instance
- `qpos` — `(frames, len(indices), 7)`, aligned with `frames.ticks`

Render every box at its `rest` pose, then animate the ones in `indices`. A box absent from
`indices` never moved by more than a millimetre; `env.history.reconstruct_qpos()` is the reference
implementation and rebuilds the full `nq_model`-wide qpos if you would rather work with that.

Recording only the movers is why an instance file is ~0.7 MB rather than ~3.6 MB. Format `/1` wrote
all 196 boxes every frame and produced ~119 MB of history per submission; do not assume old files
are cheap.

## The course preview

`docs/course-layout.json`, regenerated by `PYTHONPATH=. python tools/export_course_json.py`. It
uses the same surface shape as `apex-competition-humanoid-olympics`' exporter
(`center_m` / `size_m` / `yaw_rad` / `kind` / `rgba`), so one renderer can read both.

**It is the room shell only** — floor, dash strip, elevated finish platform, the fixed leap chain,
and the zone bands. It carries a `box_field` block that says so:

```json
"box_field": { "static": false, "sampled_per_round": true, "count": 196,
               "source": "per-instance history record: conditions.box_field and frames.boxes" }
```

That is the one place this competition genuinely cannot behave like its siblings. Parkour and
Olympics have static courses, so one exported file is the whole scene. Here the 196 boxes are drawn
per **round** from the platform's seed inside the referee, so no file checked into this repo can
describe the field a given round used. A submission viewer gets the boxes from that submission's
history record. A preview page with no submission to draw from can show the shell, and if it wants
representative clutter it has to sample a field from some seed and label it as illustrative.

Two things about the shell worth rendering correctly:

- **Completion needs height, not just distance.** The finish platform sits `1.6 m` above the deck
  (`finish.platform_top_z_m`), and a robot that reaches `x = 48 m` on the floor has *not* finished.
  Drawing a finish line alone will mislead.
- **The zone bands overlap on purpose.** `scramble` and `push` both span the whole field and
  `climb` covers its second half; they are sampling bands for box roles, not disjoint corridors.

## Terminal reasons

`completed`, `fell`, `out_of_bounds`, `timeout`, `time_limit`, `physics_glitch`, plus the
submission-fault ones (`invalid_action`, `player_error`). Same set as parkour with `time_limit`
added — the evaluation's wall-clock budget running out on that instance. It is scored on the
progress the run made, so it is a partial result and not a failure badge.
